# Abstention Ledger — ClawBio Berlin, Challenge 1

**One line:** a new ClawBio skill that parses the legacy SnpEff `EFF` field no
other skill here can read, and uses it to produce an auditable ledger of the
variants it was *not* entitled to rank — with the check, the value and the source
behind every refusal.

```bash
python3 skills/abstention-ledger/abstention_ledger.py --demo --output /tmp/al
python3 skills/abstention-ledger/tests/test_abstention_ledger.py
```

---

## Why this and not another ranker

The brief warns, verbatim:

> Do not feed the historical quartet directly to `rare-high-impact-variants`: it
> does not parse the legacy EFF field.

That is accurate, and it is checkable:
`skills/rare-high-impact-variants/rare_high_impact_variants.py:126` reads the
consequence from `MC`, `Consequence` or `ANN`. Classic SnpEff writes `EFF`. So
the skill whose own report explains the population-frequency blind spot receives
an empty consequence for every record in the format the challenge data uses.

We wrote the parser. Then the parser turned out to *be* the gate: `EFF` carries
one annotation per transcript, and collapsing it to `max(impact)` — which is the
normal thing to do — silently converts a transcript-selection decision into an
apparent biological fact.

### The sample mapping is wrong in the documentation

The data page states *"Samples ISDBM322015 to ISDBM322018 are son, father,
mother, sister."* The TSV's own column order is `SON, FATHER, SISTER, MOTHER`.
Those disagree, so we tested all 24 assignments of four sample IDs to four roles
against every genotype in the table:

| | |
|---|---|
| Assignments tested | 24 |
| Assignments reproducing all 68×4 genotypes | **1** |
| Result | `SON=ISDBM322015, FATHER=ISDBM322016, SISTER=ISDBM322017, MOTHER=ISDBM322018` |

`ISDBM322017` is the **sister**, not the mother. This agrees with Exomiser's
`Pfeiffer-quartet.ped`, which uses the same underlying exomes.

### What following the documentation costs

| Role assignment | paternal | maternal | ambiguous | no carrier parent | disagreements with supplied label |
|---|---|---|---|---|---|
| As resolved from data | **30** | **38** | 0 | 0 | **0 / 68** |
| Sister and mother swapped | 11 | 25 | 19 | 13 | **32 / 68** |

Row 1 reproduces the documented 30/38 exactly. Row 2 is what the prose ordering
produces: half the labels flip, and 13 records end up with *no carrier parent at
all* — impossible under the dataset's own stated filter, which is how the mistake
announces itself.

### The ledger

68 records in. **61 withheld, 7 reviewable.**

| Reason code | Records |
|---|---|
| `FREQUENCY_DOCUMENTED_COMMON` | 54 |
| `TRANSCRIPT_ARTIFACT` | 22 |
| `LOW_COMPLEXITY_LOCUS` | 19 |
| `ANNOTATION_SUPERSEDED` | 4 |
| `NO_FREQUENCY_RECORD` | 2 |

**54 of 68 records carry a documented population frequency at or above 1%.** The
supplied file has no frequency column of any kind, so a pipeline reading only its
input would promote all 68 with nothing to say otherwise.

The clearest single row is `1:11906068 rs5065 A>G` — `STOP_LOST`, HIGH effect, in
*NPPA*. Documented frequency **0.4183 in AFR**. Nothing in the supplied data could
have revealed that.

And only **2** records genuinely have no frequency record. Those two are reported
in their own category and never described as anything else, because absence of a
frequency is a fact about the reference database, not about the variant.

## What we refuse to do, and why

Five cohort abstentions are stated once and bound every per-record claim, because
they are properties of the dataset rather than of any variant:

| Code | Blocks |
|---|---|
| `NO_PHENOTYPE` | Any statement tying a variant to this person's clinical picture. Segregation without phenotype is arithmetic over genotypes. |
| `UNPHASED` | Any statement about two variants sharing a copy. Parent-of-origin here is Mendelian deduction, not molecular phase — the two-hit question is not unanswered, it is unaskable. |
| `SELECTION_BIAS` | Any count or burden presented as describing the family. Only records with exactly one carrier parent survive upstream filtering; totals describe the filter. |
| `HISTORICAL_ANNOTATION` | Any claim that the supplied effect labels are current evidence. |
| `NON_PROBAND_DISCLOSURE` | Treating the output as being about the proband alone. Every record states three other people's genotypes. |

A `REVIEWABLE` verdict is a claim about *our evidence*, not about the variant.

## Two bugs we found in our own work, and kept

Both are in the git history and both are documented in the code, because a
project about honest reporting that hides its own errors is not making its point.

1. **`NON_PROBAND_DISCLOSURE` started as a per-record gate.** In a
   one-carrier-parent file every record discloses a parent by construction, so it
   fired on 68/68 and made the review list trivially empty — an answer that looks
   maximally cautious and carries no information. It is now a cohort abstention.
   Regression test: `test_non_proband_carriers_is_not_a_gate`.
2. **The report said "no record" when no evidence layer had been fetched.** That
   claims we looked. A test caught it; the renderer now distinguishes
   `no record found` from `not checked`. This is the exact error the skill exists
   to catch, committed by the skill.

## Reproducing

```bash
# 1. data
mkdir -p data/challenge1 && cd data/challenge1
curl -fsSLO https://docs.clawbio.ai/hackathon/berlin/data/challenge1-b37-segregation.tsv
curl -fsSLO https://docs.clawbio.ai/hackathon/berlin/data/challenge1-b37-segregation.vcf.gz
cd -

# 2. build-matched evidence layer, one batched POST, cached to disk
python3 skills/abstention-ledger/fetch_evidence.py \
    --input data/challenge1/challenge1-b37-segregation.tsv \
    --output out/vep_grch37_cache.json

# 3. the ledger
python3 skills/abstention-ledger/abstention_ledger.py \
    --input   data/challenge1/challenge1-b37-segregation.tsv \
    --vcf     data/challenge1/challenge1-b37-segregation.vcf.gz \
    --evidence out/vep_grch37_cache.json \
    --output  out/run1

# 4. tests
python3 skills/abstention-ledger/tests/test_abstention_ledger.py
```

Python standard library only. No pip install, no API key, no GPU.

### The evidence layer, and its limits

We query `grch37.rest.ensembl.org` rather than gnomAD v4. The data is GRCh37; v4
is GRCh38-native, so a liftover would sit in the path — and a failed liftover is
indistinguishable from a missing record, which is the precise failure the brief
singles out. Build-matching removes the ambiguity.

The cost, stated in the report as well as here: that endpoint serves **gnomAD
exomes r2.1.1**, exome-only and several releases old. `NO_FREQUENCY_RECORD` is
therefore weaker evidence than it would be against v4, and we do not use it to
imply anything about a variant's frequency.

One parameter note worth passing on: the GRCh37 endpoint answers **503 Service
Unavailable** for parameters it does not support (`mane`, `af_1kg`, `af_gnomade`,
`af_gnomadg`). It reads as an outage. We wrote up "evidence layer unavailable"
before isolating `af_1kg` as the cause.

tool-call trace is the reasoning record:
